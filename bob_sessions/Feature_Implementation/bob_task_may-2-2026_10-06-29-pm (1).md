 1 | # Dev Rules v1.0.0
 2 | 
 3 | ## SOLID Principles
 4 | - **SRP**: One responsibility per component/function. Extract data fetching into custom hooks.
 5 | - **OCP**: Use extensible props (`variant`, `actions`) instead of modifying components.
 6 | - **LSP**: Extended interfaces must fulfill base interface contracts.
 7 | - **ISP**: Split large interfaces into focused ones (`Selectable`, `Displayable`).
 8 | - **DIP**: Depend on abstractions (e.g., `StorageService` interface, not `localStorage` directly).
 9 | 
10 | ## Core Principles
11 | - **DRY**: Extract repeated logic into hooks/utils (e.g., `useDebounce`).
12 | - **KISS**: Prefer readable over clever. Break logic into named steps.
13 | - **YAGNI**: Only model what's needed now. No speculative fields.
14 | 
15 | ## Clean Code
16 | - **Names**: Descriptive (`activeRecommendations` not `arr`).
17 | - **Functions**: Single purpose, <20 lines. Validate → Transform → Process pattern.
18 | - **Args**: Max 2 params; use object params for more.
19 | - **Comments**: Explain WHY not WHAT.
20 | - **Errors**: try/catch on all async. Handle `ZodError`, `Error`, and unknown cases separately.
21 | 
22 | ## TypeScript
23 | - Strict mode always on. Explicit return types required.
24 | - No `any` — use `unknown` + type guards.
25 | - `interface` for object shapes; `type` for unions/primitives.
26 |

28 | - Default to **Server Components**; use `'use client'` only when interactive.
29 | - Extract reusable logic into custom hooks (`useLocalStorage`, etc.).
30 | - Well-typed props via interfaces.

  5 | # eslint Best Practices
  6 | 
  7 | ESLint is the bedrock of our JavaScript and TypeScript code quality. This guide outlines our definitive, opinionated approach to configuring and using ESLint, focusing on modern best practices for December 2025.
  8 | 
  9 | ## 1. Core Configuration: Flat Config is Mandatory
 10 | 
 11 | Always use the new flat configuration format (`eslint.config.js`, `.mjs`, `.cjs`, or `.ts`). The legacy `.eslintrc` format is deprecated and **must not** be used.
 12 | 
 13 | ### 1.1. Base Configuration
 14 | 
 15 | Start with the recommended and strict presets for robust error prevention and stylistic consistency.
 16 | 
 17 | ```javascript
 18 | // eslint.config.js
 19 | import eslint from '@eslint/js';
 20 | import { defineConfig } from 'eslint/config';
 21 | 
 22 | export default defineConfig([
 23 |   eslint.configs.recommended, // Essential base rules
 24 |   eslint.configs.strict,     // Stricter error-prevention rules
 25 |   eslint.configs.stylistic,  // Stylistic rules (handled by Prettier, see 1.3)
 26 |   // ... other configs and rules
 27 | ]);
 28 | ```
 29 | 
 30 | ### 1.2. TypeScript Integration (Type-Aware Linting)
 31 | 
 32 | For TypeScript projects, enable type-aware linting. This provides powerful, deep analysis that catches subtle type-related issues.
 33 | 
 34 | ```javascript
 35 | // eslint.config.ts (requires `jiti` or `ts-node` for execution)
 36 | import eslint from '@eslint/js';
 37 | import { defineConfig } from 'eslint/config';
 38 | import tseslint from 'typescript-eslint';
 39 | 
 40 | export default defineConfig([
 41 |   eslint.configs.recommended,
 42 |   tseslint.configs.recommendedTypeChecked, // TypeScript recommended rules with type-checking
 43 |   tseslint.configs.strictTypeChecked,      // Stricter TypeScript rules with type-checking
 44 |   tseslint.configs.stylisticTypeChecked,   // TypeScript stylistic rules (handled by Prettier)
 45 |   {
 46 |     languageOptions: {
 47 |       parser: tseslint.parser,
 48 |       parserOptions: {
 49 |         projectService: true, // Enable TypeScript's project service for type info
 50 |         tsconfigRootDir: import.meta.dirname, // Point to your project root
 51 |       },
 52 |     },
 53 |     files: ['**/*.ts', '**/*.tsx', '**/*.mts', '**/*.cts'], // Apply to TS files
 54 |   },
 55 |   // ... other configs and rules
 56 | ]);
 57 | ```
 58 | 
 59 | **Performance Note**: Type-aware linting adds overhead. This is a worthwhile trade-off for the increased safety and quality. Rely on IDE extensions for instant feedback and run full linting in CI.

114 | ## 3. Common Patterns and Anti-patterns
115 | 
116 | Enforce these critical rules to maintain high code quality.
117 | 
118 | ### 3.1. Immutability (`prefer-const`)
119 | 
120 | Always use `const` unless a variable's value is reassigned.
121 | 
122 | ❌ BAD
123 | ```javascript
124 | let name = 'Alice';
125 | name = 'Bob'; // Reassigned, but `let` was used initially
126 | ```
127 | 
128 | ✅ GOOD
129 | ```javascript
130 | const name = 'Alice'; // Never reassigned
131 | let age = 30;
132 | age++; // Reassigned, `let` is appropriate
133 | ```
134 | 
135 | ### 3.2. Unused Variables (`no-unused-vars`)
136 | 
137 | Remove dead code. Unused variables, functions, or imports indicate cruft.
138 | 
139 | ❌ BAD
140 | ```javascript
141 | const unusedVar = 10;
142 | function doSomething() { /* ... */ } // Never called
143 | ```
144 | 
145 | ✅ GOOD
146 | ```javascript
147 | const usedVar = 10;
148 | console.log(usedVar);
149 | ```
150 | 
151 | ### 3.3. Consistent Returns (`consistent-return`)
152 | 
153 | Ensure functions either always return a value or never return one explicitly. Avoid implicit `undefined` returns.
154 | 
155 | ❌ BAD
156 | ```javascript
157 | function process(value) {
158 |   if (value > 0) {
159 |     return value * 2;
160 |   }
161 |   // Implicitly returns undefined here
162 | }
163 | ```
164 | 
165 | ✅ GOOD
166 | ```javascript
167 | function process(value) {
168 |   if (value > 0) {
169 |     return value * 2;
170 |   }
171 |   return 0; // Explicit return
172 | }
173 | 
174 | function logValue(value) {
175 |   console.log(value); // No return value expected
176 | }
177 | ```
178 | 
179 | ### 3.4. No Else Return (`no-else-return`)
180 | 
181 | Simplify conditional logic by returning early.
182 | 
183 | ❌ BAD
184 | ```javascript
185 | function getValue(condition) {
186 |   if (condition) {
187 |     return 'A';
188 |   } else {
189 |     return 'B';
190 |   }
191 | }
192 | ```
193 | 
194 | ✅ GOOD
195 | ```javascript
196 | function getValue(condition) {
197 |   if (condition) {
198 |     return 'A';
199 |   }
200 |   return 'B'; // Simplified
201 | }
202 | ```
203 | 
204 | ### 3.5. Strict Equality (`eqeqeq`)
205 | 
206 | Always use `===` and `!==` to prevent type coercion issues.
207 | 
208 | ❌ BAD
209 | ```javascript
210 | if (value == null) { /* ... */ } // Coercion
211 | ```
212 | 
213 | ✅ GOOD
214 | ```javascript
215 | if (value === null || value === undefined) { /* ... */ } // Explicit check
216 | if (value === 0) { /* ... */ } // No coercion
217 | ```
218 | 
219 | ### 3.6. No Console Logs (`no-console`)
220 | 
221 | Prevent accidental `console.log` statements from reaching production.
222 | 
223 | ```javascript
224 | // eslint.config.js
225 | export default defineConfig([
226 |   // ...
227 |   {
228 |     rules: {
229 |       'no-console': ['error', { allow: ['warn', 'error'] }], // Allow warn/error, but error on log
230 |     },
231 |   },
232 | ]);
233 | ```
234 | 
235 | ### 3.7. No Magic Numbers (`no-magic-numbers`)
236 | 
237 | Replace unexplained numeric literals with named constants for readability and maintainability.
238 | 
239 | ❌ BAD
240 | ```javascript
241 | function calculateArea(radius) {
242 |   return 3.14159 * radius * radius;
243 | }
244 | ```
245 | 
246 | ✅ GOOD
247 | ```javascript
248 | const PI = 3.14159;
249 | function calculateArea(radius) {
250 |   return PI * radius * radius;
251 | }
252 | ```

254 | ## 4. Common Pitfalls and Gotchas
255 | 
256 | ### 4.1. Avoid `eslint-disable`
257 | 
258 | **Never** use `eslint-disable` comments. They mask underlying issues, accumulate technical debt, and compromise code quality. If a rule is genuinely problematic for a specific, rare case, discuss it with the team to adjust the global configuration or create a targeted override.
259 | 
260 | ❌ BAD
261 | ```javascript
262 | // eslint-disable-next-line no-console
263 | console.log('Debug info');
264 | ```
265 | 
266 | ✅ GOOD
267 | ```javascript
268 | // Remove or refactor the problematic code.
269 | // Or, if truly necessary, configure the rule globally to allow specific cases.
270 | ```
271 | 
272 | ### 4.2. Configuration Order Matters
273 | 
274 | Ensure `eslint-config-prettier` is always the last configuration in your array to correctly disable conflicting rules.
275 | 
276 | ```javascript
277 | // eslint.config.js
278 | import eslint from '@eslint/js';
279 | import prettierConfig from 'eslint-config-prettier';
280 | 
281 | export default defineConfig([
282 |   eslint.configs.recommended,
283 |   // ... other plugins/configs like tseslint
284 |   prettierConfig, // MUST BE LAST
285 |   {
286 |     rules: {
287 |       // Your custom rules go here and will override previous configs if needed
288 |     },
289 |   },
290 | ]);
291 | ```

296 |

300 |

240 | ## Data Model
241 | 
242 | An `Interaction` response contains `outputs` — an array of typed content blocks. Each block has a `type` field:
243 | 
244 | - `text` — Generated text (`text` field)
245 | - `thought` — Model reasoning (`signature` required, optional `summary`)
246 | - `function_call` — Tool call request (`id`, `name`, `arguments`)
247 | - `function_result` — Tool result you send back (`call_id`, `name`, `result`)
248 | - `google_search_call` / `google_search_result` — Google Search tool
249 | - `code_execution_call` / `code_execution_result` — Code execution tool
250 | - `url_context_call` / `url_context_result` — URL context tool
251 | - `mcp_server_tool_call` / `mcp_server_tool_result` — Remote MCP tool
252 | - `file_search_call` / `file_search_result` — File search tool
253 | - `image` — Generated or input image (`data`, `mime_type`, or `uri`)
254 | 
255 | **Status values:** `completed`, `in_progress`, `requires_action`, `failed`, `cancelled`
256 | 
257 | 
258 | ## Key Differences from generateContent
259 | 
260 | - `startChat()` + manual history → `previous_interaction_id` (server-managed)
261 | - `sendMessage()` → `interactions.create(previous_interaction_id=...)`
262 | - `response.text` → `interaction.outputs[-1].text`
263 | - No background execution → `background=True` for async tasks
264 | - No agent access → `agent="deep-research-preview-04-2026"` or `agent="deep-research-max-preview-04-2026"`
265 | 
266 | 
267 | ## Important Notes
268 | 
269 | - Interactions are **stored by default** (`store=true`). Paid tier retains for 55 days, free tier for 1 day.
270 | - Set `store=false` to opt out, but this disables `previous_interaction_id` and `background=true`.
271 | - `tools`, `system_instruction`, and `generation_config` are **interaction-scoped** — re-specify them each turn.
272 | - **Agents require** `background=True`.
273 | - You can **mix agent and model interactions** in a conversation chain via `previous_interaction_id`.

  5 | # github-actions Best Practices
  6 | 
  7 | GitHub Actions is the backbone of modern CI/CD. Adhering to these best practices ensures your workflows are efficient, secure, and maintainable. This guide is your definitive reference for building high-quality pipelines.
  8 | 
  9 | ## 1. Workflow Design & Code Organization
 10 | 
 11 | Structure your workflows for clarity, reusability, and efficiency.
 12 | 
 13 | ### 1.1 Use Reusable Workflows and Composite Actions
 14 | 
 15 | Avoid duplication. Abstract common sequences into reusable workflows or composite actions.
 16 | 
 17 | **❌ BAD: Duplicated Steps**
 18 | ```yaml
 19 | # .github/workflows/build-frontend.yml
 20 | jobs:
 21 |   build:
 22 |     steps:
 23 |       - uses: actions/checkout@v4
 24 |       - uses: actions/setup-node@v4
 25 |         with: { node-version: '20' }
 26 |       - run: npm ci
 27 |       - run: npm run build
 28 | 
 29 | # .github/workflows/build-backend.yml
 30 | jobs:
 31 |   build:
 32 |     steps:
 33 |       - uses: actions/checkout@v4
 34 |       - uses: actions/setup-node@v4 # Duplicated setup
 35 |         with: { node-version: '20' }
 36 |       - run: npm ci # Duplicated install
 37 |       - run: npm run build:backend # Different build step
 38 | ```
 39 | 
 40 | **✅ GOOD: Reusable Workflow**
 41 | ```yaml
 42 | # .github/workflows/reusable-build.yml
 43 | on:
 44 |   workflow_call:
 45 |     inputs:
 46 |       build-script: { required: true, type: string }
 47 | jobs:
 48 |   build:
 49 |     runs-on: ubuntu-latest
 50 |     steps:
 51 |       - uses: actions/checkout@v4
 52 |       - uses: actions/setup-node@v4
 53 |         with: { node-version: '20' }
 54 |       - run: npm ci
 55 |       - run: ${{ inputs.build-script }}
 56 | 
 57 | # .github/workflows/frontend.yml
 58 | jobs:
 59 |   build:
 60 |     uses: ./.github/workflows/reusable-build.yml
 61 |     with: { build-script: 'npm run build:frontend' }
 62 | 
 63 | # .github/workflows/backend.yml
 64 | jobs:
 65 |   build:
 66 |     uses: ./.github/workflows/reusable-build.yml
 67 |     with: { build-script: 'npm run build:backend' }
 68 | ```

 71 | 
 72 | Use clear, descriptive names for jobs and steps. This improves readability and debugging.
 73 | 
 74 | **❌ BAD: Vague Naming**
 75 | ```yaml
 76 | jobs:
 77 |   job1:
 78 |     steps:
 79 |       - run: echo "hello"
 80 |       - run: npm test
 81 | 
 82 | # logs will show 'Run echo "hello"' and 'Run npm test'
 83 | ```

 86 | ```yaml
 87 | jobs:
 88 |   lint-and-test:
 89 |     name: Lint & Test Code
 90 |     steps:
 91 |       - name: Run ESLint
 92 |         run: npm run lint
 93 |       - name: Run Unit Tests
 94 |         run: npm test
 95 | ```

 98 | 
 99 | Test across multiple OSes, Node.js versions, or other configurations efficiently.
100 | 
101 | **❌ BAD: Separate Jobs for Each Variant**
102 | ```yaml
103 | jobs:
104 |   test-node-18-ubuntu:
105 |     runs-on: ubuntu-latest
106 |     steps:
107 |       - uses: actions/setup-node@v4
108 |         with: { node-version: '18' }
109 |       - run: npm test
110 |   test-node-20-ubuntu:
111 |     runs-on: ubuntu-latest
112 |     steps:
113 |       - uses: actions/setup-node@v4
114 |         with: { node-version: '20' }
115 |       - run: npm test
116 | ```

121 |   test:
122 |     runs-on: ${{ matrix.os }}
123 |     strategy:
124 |       matrix:
125 |         node-version: ['18', '20']

128 |       - uses: actions/setup-node@v4

237 | Protect your secrets and mitigate common attack vectors.
238 | 
239 | ### 4.1 Store All Secrets in GitHub Secrets
240 | 
241 | Never hardcode sensitive values. Use GitHub's built-in secret management.

256 | 
257 | Set default `GITHUB_TOKEN` permissions to read-only, then elevate only when necessary for specific jobs.
258 | 
259 | **❌ BAD: Overly Permissive Default**

263 |   build:
264 |     # ...
265 |   deploy:

282 |       # ...

  5 | # Playwright Best Practices
  6 | 
  7 | Playwright is the gold standard for reliable E2E testing. These rules ensure your tests are fast, stable, and easy to maintain, aligning with modern 2025 development standards for reliability, quality, and structure.
  8 | 
  9 | ## 1. Always Use `@playwright/test`
 10 | 
 11 | Leverage the official test runner for built-in fixtures, isolation, and web-first assertions. Avoid the low-level `playwright` library for E2E tests.
 12 | 
 13 | ❌ BAD: Using `playwright` directly
 14 | ```typescript
 15 | import { chromium } from 'playwright';
 16 | // ... manual browser/context setup and teardown
 17 | const browser = await chromium.launch();
 18 | const page = await browser.newPage();
 19 | // ...
 20 | await browser.close();
 21 | ```
 22 | 
 23 | ✅ GOOD: Using `@playwright/test`
 24 | ```typescript
 25 | import { test, expect } from '@playwright/test';
 26 | test('should navigate to home', async ({ page }) => {
 27 |   await page.goto('/');
 28 |   await expect(page).toHaveTitle(/Home/);
 29 | });
 30 | ```
 31 | 
 32 | ## 2. Prioritize Robust Locators
 33 | 
 34 | Use Playwright's built-in Locators API, favoring user-facing attributes over brittle CSS selectors. This drastically improves test stability.
 35 | 
 36 | ❌ BAD: Fragile, implementation-dependent selectors
 37 | ```typescript
 38 | await page.locator('div.container > ul > li:nth-child(2) > button').click();
 39 | ```
 40 | 
 41 | ✅ GOOD: Semantic, user-facing locators
 42 | ```typescript
 43 | await page.getByRole('button', { name: 'Add to Cart' }).click();
 44 | await page.getByLabel('Username').fill('testuser');
 45 | await page.getByTestId('product-item-123').click();
 46 | ```
 47 | 
 48 | ## 3. Embrace Web-First Assertions
 49 | 
 50 | Playwright's `expect` assertions automatically retry until conditions are met, eliminating manual waits and flakiness. Never use `page.waitForTimeout()`.
 51 | 
 52 | ❌ BAD: Manual, flaky waits and generic assertions
 53 | ```typescript
 54 | await page.waitForTimeout(2000); // 🚨 Flaky!
 55 | const title = await page.title();
 56 | assert.equal(title, 'My Page'); // 🚨 Not web-first
 57 | ```
 58 | 
 59 | ✅ GOOD: Reliable, auto-retrying assertions
 60 | ```typescript
 61 | await expect(page).toHaveTitle(/My Page/);
 62 | await expect(page.getByText('Welcome')).toBeVisible();
 63 | await expect(page.getByRole('checkbox')).toBeChecked();
 64 | ```
 65 | 
 66 | ## 4. Implement the Page Object Model (POM)
 67 | 
 68 | Encapsulate selectors and actions within dedicated classes. This improves readability, reusability, and maintainability.
 69 | 
 70 | ❌ BAD: Repeated selectors and logic across tests
 71 | ```typescript
 72 | // test-login.spec.ts
 73 | await page.getByLabel('Username').fill('user');
 74 | await page.getByLabel('Password').fill('pass');
 75 | await page.getByRole('button', { name: 'Login' }).click();
 76 | 
 77 | // test-profile.spec.ts
 78 | // ... same login steps repeated ...
 79 | ```
 80 | 
 81 | ✅ GOOD: Centralized Page Object
 82 | ```typescript
 83 | // pages/LoginPage.ts
 84 | import { Page, Locator } from '@playwright/test';
 85 | 
 86 | export class LoginPage {
 87 |   readonly page: Page;
 88 |   readonly usernameInput: Locator;
 89 |   readonly passwordInput: Locator;
 90 |   readonly loginButton: Locator;
 91 | 
 92 |   constructor(page: Page) {
 93 |     this.page = page;
 94 |     this.usernameInput = page.getByLabel('Username');
 95 |     this.passwordInput = page.getByLabel('Password');
 96 |     this.loginButton = page.getByRole('button', { name: 'Login' });
 97 |   }
 98 | 
 99 |   async navigate() {
100 |     await this.page.goto('/login');
101 |   }
102 | 
103 |   async login(username: string, password: string) {
104 |     await this.usernameInput.fill(username);
105 |     await this.passwordInput.fill(password);
106 |     await this.loginButton.click();
107 |   }
108 | }
109 | 
110 | // tests/login.spec.ts
111 | import { test, expect } from '@playwright/test';
112 | import { LoginPage } from '../pages/LoginPage';
113 | 
114 | test('should successfully log in', async ({ page }) => {
115 |   const loginPage = new LoginPage(page);
116 |   await loginPage.navigate();
117 |   await loginPage.login('testuser', 'password');
118 |   await expect(page).toHaveURL(/dashboard/);
119 | });
120 | ```
121 | 
122 | ## 5. Optimize Performance with Auth State & Route Blocking
123 | 
124 | Reduce test execution time by reusing authenticated sessions and blocking unnecessary network requests.
125 | 
126 | ❌ BAD: Logging in for every test and loading all assets
127 | ```typescript
128 | test('view profile', async ({ page }) => {
129 |   await page.goto('/login');
130 |   await page.getByLabel('Username').fill('user');
131 |   await page.getByLabel('Password').fill('pass');
132 |   await page.getByRole('button', { name: 'Login' }).click();
133 |   await page.goto('/profile'); // Loads all images, analytics, etc.
134 | });
135 | ```
136 | 
137 | ✅ GOOD: Reusing auth state and blocking requests
138 | ```typescript
139 | // playwright.config.ts
140 | import { defineConfig } from '@playwright/test';
141 | export default defineConfig({
142 |   use: {
143 |     storageState: 'playwright-auth.json', // Path to save/load auth state
144 |   },
145 | });
146 | 
147 | // global-setup.ts (run once before all tests)
148 | import { chromium, expect } from '@playwright/test';
149 | export default async function globalSetup() {
150 |   const browser = await chromium.launch();
151 |   const page = await browser.newPage();
152 |   await page.goto('/login');
153 |   await page.getByLabel('Username').fill('testuser');
154 |   await page.getByLabel('Password').fill('password');
155 |   await page.getByRole('button', { name: 'Login' }).click();
156 |   await expect(page).toHaveURL(/dashboard/);
157 |   await page.context().storageState({ path: 'playwright-auth.json' });
158 |   await browser.close();
159 | }
160 | 
161 | // tests/profile.spec.ts
162 | import { test, expect } from '@playwright/test';
163 | test('should display user profile', async ({ page, context }) => {
164 |   // Block unnecessary resources for faster tests
165 |   await context.route('**/*.{png,jpg,jpeg,gif,webp,svg,css}', route => route.abort());
166 |   await page.goto('/profile'); // Automatically uses saved auth state
167 |   await expect(page.getByText('Welcome, testuser!')).toBeVisible();
168 | });
169 | ```

172 | 
173 | Isolate your UI tests from backend flakiness by intercepting and mocking API responses.
174 | 
175 | ❌ BAD: Relying on a live, potentially unstable backend
176 | ```typescript

  5 | # react Best Practices
  6 | 
  7 | This guide outlines the non-negotiable standards for building React applications within our team. Adherence ensures predictable behavior, simplifies debugging, and enables future optimizations.
  8 | 
  9 | ## 1. Core React Principles: Purity & Rules of Hooks
 10 | 
 11 | Components and Hooks **must be pure**. They should always return the same output given the same inputs (props, state, context) and not cause side effects during rendering. Obey the [Rules of Hooks](https://react.dev/reference/rules/rules-of-hooks) without exception.
 12 | 
 13 | ### ❌ BAD: Impure component / Side effect in render
 14 | ```tsx
 15 | function ProductList({ products }) {
 16 |   // ❌ Modifies external data during render
 17 |   products.sort((a, b) => a.name.localeCompare(b.name));
 18 |   return (/* ... */);
 19 | }
 20 | 
 21 | function MyComponent() {
 22 |   // ❌ Hook called conditionally
 23 |   if (Math.random() > 0.5) {
 24 |     const [count, setCount] = useState(0);
 25 |   }
 26 |   return (/* ... */);
 27 | }
 28 | ```
 29 | 
 30 | ### ✅ GOOD: Pure component / Correct Hook usage
 31 | ```tsx
 32 | import { useMemo, useState } from 'react';
 33 | 
 34 | function ProductList({ products }) {
 35 |   // ✅ Sort data immutably or memoize if expensive
 36 |   const sortedProducts = useMemo(() => 
 37 |     [...products].sort((a, b) => a.name.localeCompare(b.name)),
 38 |     [products]
 39 |   );
 40 |   return (/* ... */);
 41 | }
 42 | 
 43 | function MyComponent() {
 44 |   // ✅ Hooks always at the top level
 45 |   const [count, setCount] = useState(0); 
 46 |   // ... conditional logic after hooks
 47 |   return (/* ... */);
 48 | }
 49 | ```
 50 | 
 51 | ## 2. Code Organization & Naming
 52 | 
 53 | Organize code by **feature** using the `bulletproof-react` pattern. Use TypeScript (`.tsx`) for all components.
 54 | 
 55 | *   **One Component Per File**: Except for small, pure, stateless components closely related to a parent.
 56 | *   **Naming**:
 57 |     *   Components: `PascalCase` (e.g., `UserProfile.tsx`)
 58 |     *   Custom Hooks: `use` prefix + `PascalCase` (e.g., `useAuth.ts`)
 59 |     *   Functions/Variables: `camelCase`
 60 |     *   CSS Classes: `kebab-case` (via CSS Modules or utility classes)
 61 | 
 62 | ### ✅ GOOD: Feature-based structure
 63 | ```
 64 | src/
 65 | ├── features/
 66 | │   ├── auth/
 67 | │   │   ├── components/
 68 | │   │   │   ├── LoginForm.tsx
 69 | │   │   │   └── AuthButton.tsx
 70 | │   │   ├── hooks/

 84 | ## 3. Component Design & Patterns
 85 | 
 86 | Prioritize **function components with Hooks**. Separate concerns into "smart" (data/logic) and "dumb" (presentational) components.
 87 | 
 88 | ### ❌ BAD: Class components / Mixed concerns
 89 | ```tsx
 90 | // ❌ Class component (avoid)
 91 | class UserProfile extends React.Component { /* ... */ }
 92 | 
 93 | // ❌ Component fetches data AND renders complex UI
 94 | function ProductPage() {
 95 |   const [products, setProducts] = useState([]);
 96 |   useEffect(() => { /* fetch products */ }, []);
 97 |   return (/* complex product list UI */);
 98 | }
 99 | ```
100 | 
101 | ### ✅ GOOD: Function components / Separation of concerns
102 | ```tsx
103 | // ✅ Use function components with hooks
104 | function UserProfile({ user }) { /* ... */ }
105 | 
106 | // ✅ Smart component (container) handles data fetching
107 | function ProductListContainer() {
108 |   const { products, isLoading } = useProducts(); // Custom hook for data
109 |   if (isLoading) return <LoadingSpinner />;
110 |   return <ProductList products={products} />; // Renders dumb component

113 | // ✅ Dumb component (presentational) focuses on UI
114 | function ProductList({ products }) {

117 |       {products.map(product => <ProductCard key={product.id} product={product} />)}
118 |     </ul>
119 |   );
120 | }

123 | ## 4. State Management
124 | 
125 | Start with **local state (`useState`, `useReducer`)**. Lift state up when necessary. Use **Context API** for global state that rarely changes. For complex global state, use dedicated libraries (e.g., Zustand, Jotai, Redux Toolkit). **Avoid prop drilling.**
126 | 
127 | ### ❌ BAD: Prop drilling
128 | ```tsx
129 | function Grandparent() {
130 |   const [theme, setTheme] = useState('dark');
131 |   return <Parent theme={theme} setTheme={setTheme} />;
132 | }
133 | function Parent({ theme, setTheme }) {
134 |   return <Child theme={theme} setTheme={setTheme} />;
135 | }
136 | function Child({ theme, setTheme }) {
137 |   return <Button onClick={() => setTheme('light')}>Toggle Theme</Button>;
138 | }
139 | ```
140 | 
141 | ### ✅ GOOD: Context API for global state
142 | ```tsx
143 | import { createContext, useContext, useState, ReactNode } from 'react';
144 | 
145 | type Theme = 'light' | 'dark';
146 | type ThemeContextType = { theme: Theme; toggleTheme: () => void };
147 | 
148 | const ThemeContext = createContext<ThemeContextType | undefined>(undefined);
149 | 
150 | export function ThemeProvider({ children }: { children: ReactNode }) {
151 |   const [theme, setTheme] = useState<Theme>('dark');
152 |   const toggleTheme = () => setTheme(prev => (prev === 'dark' ? 'light' : 'dark'));
153 |   return (
154 |     <ThemeContext.Provider value={{ theme, toggleTheme }}>
155 |       {children}
156 |     </ThemeContext.Provider>
157 |   );
158 | }
159 | 
160 | export const useTheme = () => {
161 |   const context = useContext(ThemeContext);
162 |   if (context === undefined) {
163 |     throw new Error('useTheme must be used within a ThemeProvider');
164 |   }
165 |   return context;
166 | };
167 | 
168 | // Usage:
169 | function MyComponent() {
170 |   const { theme, toggleTheme } = useTheme();
171 |   return <button onClick={toggleTheme}>Current theme: {theme}</button>;
172 | }
173 | ```

175 | ## 5. Performance & Optimization
176 | 
177 | Optimize only when profiling indicates a bottleneck. Use `React.memo`, `useCallback`, `useMemo` judiciously.
178 | 
179 | ### ❌ BAD: Premature optimization / Incorrect memoization
180 | ```tsx
181 | // ❌ Memoizing a component that re-renders frequently or has no expensive props
182 | const MyButton = React.memo(({ onClick, children }) => <button onClick={onClick}>{children}</button>);
183 | 
184 | // ❌ Callback with missing dependency, causing stale closure
185 | function Parent() {
186 |   const [count, setCount] = useState(0);
187 |   const handleClick = useCallback(() => {
188 |     console.log(count); // ❌ 'count' is stale if not in dependency array
189 |   }, []); 
190 |   return <Child onClick={handleClick} />;
191 | }
192 | ```
193 | 
194 | ### ✅ GOOD: Targeted optimization / Correct dependencies
195 | ```tsx
196 | import React, { useCallback, useMemo, useState } from 'react';
197 | 
198 | // ✅ Memoize only if component is expensive AND props are stable
199 | const ExpensiveList = React.memo(({ items }) => {
200 |   console.log('Rendering ExpensiveList');
201 |   return (/* ... render many items ... */);
202 | });
203 | 
204 | function Parent() {
205 |   const [count, setCount] = useState(0);
206 |   // ✅ Callback with correct dependencies
207 |   const handleClick = useCallback(() => {
208 |     setCount(prev => prev + 1); // Use functional update to avoid 'count' in deps
209 |   }, []); 
210 | 
211 |   // ✅ Memoize expensive calculations
212 |   const computedValue = useMemo(() => {
213 |     // ... heavy computation based on count ...
214 |     return count * 2;
215 |   }, [count]);
216 | 
217 |   return (
218 |     <>
219 |       <ExpensiveList items={[{ id: 1, name: 'Item 1' }]} /> {/* Example usage */}
220 |       <Child onClick={handleClick} />
221 |       <p>Count: {count}, Computed: {computedValue}</p>
222 |     </>
223 |   );
224 | }
225 | // Child component that receives the memoized callback
226 | const Child = React.memo(({ onClick }: { onClick: () => void }) => {
227 |   console.log('Rendering Child');
228 |   return <button onClick={onClick}>Increment</button>;
229 | });
230 | ```

233 | 
234 | *   **Never mutate props or state directly.** Always create new objects/arrays.

  5 | # Redis Best Practices
  6 | 
  7 | Redis is a powerful, single-threaded, in-memory database. Its efficiency hinges on how you interact with it. Follow these rules to ensure your applications are performant, scalable, and resilient.
  8 | 
  9 | ## 1. Data Modeling & Key Design
 10 | 
 11 | Efficient key design is paramount for performance and memory.
 12 | 
 13 | ### 1.1. Use Hierarchical Key Naming
 14 | 
 15 | Adopt a consistent, hierarchical key naming convention. This improves readability and allows for logical grouping.
 16 | 
 17 | ❌ BAD
 18 | ```redis
 19 | user:1:name
 20 | user:1:email
 21 | product:123:details
 22 | order:456:items
 23 | ```
 24 | 
 25 | ✅ GOOD
 26 | ```redis
 27 | user:1:profile:name
 28 | user:1:profile:email
 29 | product:123:data
 30 | order:456:cart:items
 31 | ```
 32 | *Rationale*: Clearer separation, better organization.
 33 | 
 34 | ### 1.2. Avoid Large Objects in Single Keys
 35 | 
 36 | Do not store multi-megabyte objects in a single key. Break down complex data into hashes or streams. This improves eviction, replication, and memory efficiency.
 37 | 
 38 | ❌ BAD
 39 | ```python
 40 | # Storing a large JSON object directly as a string
 41 | user_data = {"id": 1, "name": "Alice", "preferences": {...large_object...}, "history": [...many_items...]}
 42 | redis_client.set(f"user:1:data", json.dumps(user_data))
 43 | ```
 44 | 
 45 | ✅ GOOD
 46 | ```python
 47 | # Using a Redis Hash for structured data
 48 | redis_client.hset(f"user:1:profile", mapping={
 49 |     "id": 1,
 50 |     "name": "Alice",
 51 |     "email": "alice@example.com"
 52 | })
 53 | # Storing large, evolving data in a stream or separate keys
 54 | redis_client.xadd(f"user:1:activity_stream", {"action": "login", "timestamp": time.time()})
 55 | ```
 56 | *Rationale*: Hashes are optimized for field-value pairs, streams for time-series data. This keeps individual values small, aiding Redis's single-threaded nature.
 57 | 
 58 | ### 1.3. Use Hashtags for Multi-Key Operations in Clusters
 59 | 
 60 | When performing multi-key operations (e.g., transactions, Lua scripts) in a Redis Cluster, ensure all involved keys reside on the same hash slot by using hashtags.
 61 | 
 62 | ❌ BAD
 63 | ```python
 64 | # These keys will likely be on different slots, causing MOVED errors in a cluster
 65 | redis_client.mget("user:1:profile", "user:1:orders")
 66 | ```
 67 | 
 68 | ✅ GOOD
 69 | ```python
 70 | # Keys with the same hashtag ({...}) are guaranteed to be on the same slot
 71 | redis_client.mget("{user:1}:profile", "{user:1}:orders")
 72 | ```
 73 | *Rationale*: Hashtags (`{...}`) force Redis to hash only the content within the braces, ensuring co-location for atomic operations.
 74 | 
 75 | ### 1.4. Never Use Numbered Databases (`SELECT`)
 76 | 
 77 | Numbered databases (`SELECT`) are an anti-pattern. They provide false isolation and are not supported by Redis Cluster.
 78 | 
 79 | ❌ BAD
 80 | ```python
 81 | redis_client.select(1) # Using database 1
 82 | redis_client.set("mykey", "myvalue")
 83 | ```
 84 | 
 85 | ✅ GOOD
 86 | ```python
 87 | # Use distinct key prefixes instead of numbered databases
 88 | redis_client.set("app:cache:mykey", "myvalue")
 89 | redis_client.set("app:sessions:mykey", "myvalue")
 90 | ```
 91 | *Rationale*: Numbered databases share the same underlying instance, meaning operations like `KEYS` on one database block all others. Key prefixes are the correct way to logically separate data.
 92 | 
 93 | ## 2. Connection & Memory Management
 94 | 
 95 | Proper client configuration and instance sizing are critical.
 96 | 
 97 | ### 2.1. Always Use Connection Pooling
 98 | 
 99 | Creating new TCP connections for every Redis command is expensive. Use a connection pool to reuse connections.
100 | 
101 | ❌ BAD
102 | ```python
103 | # Creates a new connection for each operation
104 | redis_client = redis.Redis(host='localhost', port=6379)
105 | redis_client.set("key", "value")
106 | redis_client.get("key")
107 | ```
108 | 
109 | ✅ GOOD
110 | ```python
111 | # Uses a connection pool (default for most clients, but explicitly shown)
112 | pool = redis.ConnectionPool(host='localhost', port=6379, max_connections=10)
113 | redis_client = redis.Redis(connection_pool=pool)
114 | redis_client.set("key", "value")
115 | redis_client.get("key")
116 | ```
117 | *Rationale*: Connection pooling significantly reduces overhead and improves latency.
118 | 
119 | ### 2.2. Monitor and Manage Memory Usage
120 | 
121 | Configure `maxmemory` policies and lazy freeing. Provision instances with sufficient headroom for write spikes.
122 | 
123 | ```redis
124 | # redis.conf
125 | maxmemory 8gb             # Set maximum memory usage
126 | maxmemory-policy allkeys-lru # Evict least recently used keys when memory limit is reached
127 | lazyfree-lazy-eviction yes # Asynchronously free memory during eviction
128 | lazyfree-lazy-expire yes   # Asynchronously free memory during key expiration
129 | lazyfree-lazy-server-del yes # Asynchronously free memory when deleting keys
130 | ```
131 | *Rationale*: Proactive memory management prevents OOM errors and maintains predictable performance.
132 | 
133 | ## 3. Cluster-Aware Client Usage
134 | 
135 | When using Redis Cluster, your client must understand the cluster topology.
136 | 
137 | ### 3.1. Use Cluster-Aware Clients
138 | 
139 | Always use client libraries specifically designed for Redis Cluster (e.g., `redis-py-cluster`, Lettuce, GLIDE). These clients handle slot mapping and `MOVED` redirections automatically.
140 | 
141 | ❌ BAD
142 | ```python
143 | # This client is not cluster-aware and will fail or perform poorly
144 | import redis
145 | client = redis.Redis(host='cluster-node-1', port=6379)
146 | client.set("mykey", "myvalue")
147 | ```
148 | 
149 | ✅ GOOD
150 | ```python
151 | # Use a cluster-aware client
152 | from redis.cluster import RedisCluster
153 | client = RedisCluster(host='cluster-node-1', port=6379, decode_responses=True)
154 | client.set("mykey", "myvalue")
155 | ```
156 | *Rationale*: Cluster-aware clients prevent `MOVED` errors and ensure requests are routed to the correct node, enabling seamless scaling.
157 | 
158 | ### 3.2. Implement Exponential Backoff for Client Discovery
159 | 
160 | When clients disconnect or need to discover cluster topology, implement exponential backoff with jitter on retries to prevent overwhelming the cluster with `CLUSTER SLOTS` commands.
161 | 
162 | ```python
163 | import time
164 | import random
165 | from redis.cluster import RedisCluster, RedisClusterException
166 | 
167 | def connect_with_backoff(hosts, max_retries=5):
168 |     for i in range(max_retries):
169 |         try:
170 |             client = RedisCluster(startup_nodes=hosts, decode_responses=True)
171 |             client.ping() # Verify connection
172 |             return client
173 |         except RedisClusterException as e:
174 |             print(f"Connection failed (attempt {i+1}/{max_retries}): {e}")
175 |             sleep_time = (2 ** i) + random.uniform(0, 1) # Exponential backoff with jitter
176 |             time.sleep(sleep_time)
177 |     raise ConnectionError("Failed to connect to Redis Cluster after multiple retries")
178 | 
179 | # Example usage
180 | startup_nodes = [{"host": "node1", "port": 6379}, {"host": "node2", "port": 6379}]
181 | redis_cluster_client = connect_with_backoff(startup_nodes)
182 | ```
183 | *Rationale*: Prevents a thundering herd problem during cluster reconfigurations or outages.
184 | 
185 | ## 4. Query Optimization & Batch Operations
186 | 
187 | Minimize network round-trips and avoid resource-intensive commands.
188 | 
189 | ### 4.1. Use Pipelining for Batch Operations
190 | 
191 | Group multiple commands into a single request to reduce network latency.
192 | 
193 | ❌ BAD
194 | ```python
195 | # Multiple round-trips
196 | redis_client.set("key1", "value1")
197 | redis_client.set("key2", "value2")
198 | redis_client.get("key1")
199 | redis_client.get("key2")
200 | ```
201 | 
202 | ✅ GOOD
203 | ```python
204 | # Single round-trip for multiple commands
205 | pipe = redis_client.pipeline()
206 | pipe.set("key1", "value1")
207 | pipe.set("key2", "value2")
208 | pipe.get("key1")
209 | pipe.get("key2")
210 | results = pipe.execute()
211 | ```
212 | *Rationale*: Pipelining batches commands, sending them in one go and receiving all results at once, drastically improving throughput.
213 | 
214 | ### 4.2. Avoid `KEYS` in Production
215 | 
216 | `KEYS` is a blocking, O(N) operation that can halt your Redis server. Use `SCAN` for iterating keys.
217 | 
218 | ❌ BAD
219 | ```python
220 | # Blocks the server for large datasets
221 | all_keys = redis_client.keys("user:*")
222 | ```
223 | 
224 | ✅ GOOD
225 | ```python
226 | # Iterates keys incrementally without blocking
227 | cursor = 0
228 | while True:
229 |     cursor, keys = redis_client.scan(cursor, match="user:*", count=100)
230 |     for key in keys:
231 |         # Process key
232 |         pass
233 |     if cursor == 0:
234 |         break
235 | ```
236 | *Rationale*: `SCAN` provides an iterator-like interface, distributing the work over multiple calls and preventing server stalls.
237 | 
238 | ### 4.3. Limit Result Sets for Collections
239 | 
240 | Avoid fetching entire large lists, sets, or hashes. Use `LRANGE` with limits, `HSCAN`, or `SSCAN`.
241 | 
242 | ❌ BAD
243 | ```python
244 | # Fetches all members of a potentially huge set
245 | all_members = redis_client.smembers("my_large_set")
246 | ```
247 | 
248 | ✅ GOOD
249 | ```python
250 | # Iterates members incrementally
251 | cursor = 0
252 | while True:
253 |     cursor, members = redis_client.sscan(cursor, name="my_large_set", count=100)
254 |     for member in members:
255 |         # Process member
256 |         pass
257 |     if cursor == 0:
258 |         break
259 | ```
260 | *Rationale*: Prevents excessive memory usage on both the server and client, and reduces network transfer.
261 |

269 | 
270 | ❌ BAD
271 | ```redis

274 | # requirepass foobared
275 | ```
276 | 
277 | ✅ GOOD
278 | ```redis

281 | ```
282 | *Rationale*: An unprotected Redis instance is a common target for attackers.

285 | 
286 | Deploy Redis behind a firewall, in a private network, or within a VPC. Only allow access from trusted application servers.
287 | 
288 | *Rationale*: Reduces the attack surface by preventing direct public access.

  4 | ---
  5 | # TypeScript Best Practices (for JS/JSX Type-Checking)
  6 | 
  7 | This guide outlines essential TypeScript best practices for teams working with JavaScript or JSX files that are type-checked by TypeScript (e.g., via `tsconfig.json` with `allowJs` and/or JSDoc annotations). While many examples use native TypeScript syntax for clarity and conciseness, the underlying principles and type-safety benefits apply directly to your `.js`/`.jsx` codebase.
  8 | 
  9 | ## 1. Enable Strict Mode in `tsconfig.json`
 10 | 
 11 | This is the single most impactful change you can make. `strict: true` enables a suite of crucial checks that catch the vast majority of common type-related bugs at compile time.
 12 | 
 13 | **Action**: Ensure your `tsconfig.json` includes:
 14 | 
 15 | ```json
 16 | // tsconfig.json
 17 | {
 18 |   "compilerOptions": {
 19 |     "strict": true, // Enables all strict type-checking options
 20 |     "noImplicitAny": true, // Catches untyped variables/parameters
 21 |     "strictNullChecks": true, // Prevents `null`/`undefined` access without checks
 22 |     "strictPropertyInitialization": true, // Ensures class properties are initialized
 23 |     "allowJs": true, // Crucial for type-checking .js/.jsx files
 24 |     "checkJs": true, // Enables type-checking in .js/.jsx files
 25 |     // ... other options
 26 |   },
 27 |   "include": ["**/*.js", "**/*.jsx"] // Ensure your JS/JSX files are included
 28 | }
 29 | ```
 30 | 
 31 | ## 2. Define Clear Type Contracts
 32 | 
 33 | Use interfaces and type aliases to describe the shape of your data, especially for API payloads, component props, and complex objects. For `.js`/`.jsx` files, leverage JSDoc to apply these types.
 34 | 
 35 | ### ✅ GOOD: Interfaces for Object Shapes & Classes
 36 | 
 37 | Interfaces are ideal for defining the shape of objects and for implementing explicit contracts when working with classes. Define these in `.d.ts` or `.ts` files, then reference them in JSDoc.
 38 | 
 39 | ```typescript
 40 | // types.d.ts or types.ts
 41 | interface UserProfile {
 42 |   id: string;
 43 |   name: string;
 44 |   email: string;
 45 |   age?: number; // Optional property
 46 | }
 47 | 
 48 | interface Point {
 49 |   readonly x: number;
 50 |   readonly y: number;
 51 | }
 52 | ```
 53 | 
 54 | ```javascript
 55 | // user-service.js
 56 | /**
 57 |  * @typedef {import('./types').UserProfile} UserProfile
 58 |  */
 59 | 
 60 | /**
 61 |  * @param {UserProfile} user
 62 |  * @returns {string}
 63 |  */
 64 | export function greetUser(user) {
 65 |   return `Hello, ${user.name}!`;
 66 | }
 67 | ```
 68 | 
 69 | ### ✅ GOOD: Type Aliases for Complex Types & Unions
 70 | 
 71 | Type aliases are powerful for defining unions, intersections, primitive aliases, and tuples. Define these in `.d.ts` or `.ts` files, then reference them in JSDoc.
 72 | 
 73 | ```typescript
 74 | // types.d.ts or types.ts
 75 | type ID = string | number;
 76 | type UserRole = "admin" | "user" | "guest"; // Strict literal type
 77 | type Coords = [number, number];
 78 | ```
 79 | 
 80 | ```javascript
 81 | // auth-service.js
 82 | /**
 83 |  * @typedef {import('./types').ID} ID
 84 |  * @typedef {import('./types').UserRole} UserRole
 85 |  */
 86 | 
 87 | /**
 88 |  * @param {ID} userId
 89 |  * @param {UserRole} role
 90 |  * @returns {void}
 91 |  */
 92 | export function assignRole(userId, role) {
 93 |   console.log(`User ${userId} assigned role: ${role}`);
 94 | }
 95 | ```
 96 | 
 97 | ## 3. Avoid `any` and Prefer `unknown` for Untyped Data
 98 | 
 99 | `any` completely bypasses TypeScript's checks, reintroducing JavaScript's runtime errors. `unknown` is a safer alternative that forces you to narrow the type before use.
100 | 
101 | ### ❌ BAD: Using `any`
102 | 
103 | ```javascript
104 | // data-processor.js
105 | /**
106 |  * @param {any} data // Bypasses all type checks
107 |  */
108 | export function processDataBad(data) {
109 |   // No type safety here, data.foo might not exist
110 |   console.log(data.foo.bar);
111 | }
112 | ```
113 | 
114 | ### ✅ GOOD: Using `unknown` (and Type Guards)
115 | 
116 | When dealing with data from external sources (e.g., API responses), use `unknown` and then narrow its type using runtime checks.
117 | 
118 | ```javascript
119 | // data-processor.js
120 | /**
121 |  * @param {unknown} data // Forces runtime checks
122 |  */
123 | export function processDataGood(data) {
124 |   if (typeof data === 'object' && data !== null && 'foo' in data) {
125 |     /** @type {{ foo: { bar: string } }} */
126 |     const typedData = data; // Type assertion after narrowing
127 |     console.log(typedData.foo.bar);
128 |   } else {
129 |     console.error('Invalid data structure');
130 |   }
131 | }
132 | ```
133 | 
134 | ## 4. Implement Robust Runtime Type Validation (Type Guards)
135 | 
136 | TypeScript's compile-time checks are erased at runtime. For data from external sources (APIs, user input), you *must* perform runtime validation to prevent crashes.
137 | 
138 | ### ✅ GOOD: `typeof` for Primitives
139 | 
140 | ```javascript
141 | // utils.js
142 | /**
143 |  * @param {unknown} value
144 |  * @returns {boolean}
145 |  */
146 | export function isString(value) {
147 |   return typeof value === 'string';
148 | }
149 | 
150 | /**
151 |  * @param {unknown} value
152 |  * @returns {boolean}
153 |  */
154 | export function isNumber(value) {
155 |   return typeof value === 'number' && !isNaN(value);
156 | }
157 | ```
158 | 
159 | ### ✅ GOOD: Custom Type Guards for Complex Objects
160 | 
161 | For interfaces or complex object shapes, create custom functions that perform runtime checks and act as type predicates.
162 | 
163 | ```typescript
164 | // types.d.ts or types.ts
165 | interface Product {
166 |   id: string;
167 |   name: string;
168 |   price: number;
169 | }
170 | 
171 | // Custom type guard (can be in a .ts file, or its logic used directly in .js)
172 | /**
173 |  * @param {unknown} obj
174 |  * @returns {obj is Product}
175 |  */
176 | function isProduct(obj) {
177 |   return (
178 |     typeof obj === 'object' && obj !== null &&
179 |     'id' in obj && typeof obj.id === 'string' &&
180 |     'name' in obj && typeof obj.name === 'string' &&
181 |     'price' in obj && typeof obj.price === 'number'
182 |   );
183 | }
184 | ```
185 | 
186 | ```javascript
187 | // api-client.js
188 | /**
189 |  * @typedef {import('./types').Product} Product
190 |  * @type {typeof import('./types').isProduct}
191 |  */
192 | import { isProduct } from './types'; // Assuming isProduct is exported from types.ts/d.ts
193 | 
194 | /**
195 |  * @param {unknown} apiResponse
196 |  */
197 | export function handleApiResponse(apiResponse) {
198 |   if (isProduct(apiResponse)) {
199 |     // TypeScript now knows apiResponse is Product here
200 |     console.log(`Fetched product: ${apiResponse.name} at $${apiResponse.price}`);
201 |   } else {
202 |     console.error('API response is not a valid Product:', apiResponse);
203 |   }
204 | }
205 | ```
206 | 
207 | ## 5. Prefer Union Types over Traditional Enums
208 | 
209 | For simple sets of related constants, strict literal union types (`"admin" | "user"`) are generally preferred over TypeScript's `enum` keyword because they offer better type safety and simpler runtime representation. If you must use enums, prefer `const enum` or string enums.
210 | 
211 | ### ❌ BAD: Numeric Enums
212 | 
213 | ```typescript
214 | // In a .ts file or JSDoc
215 | enum UserStatus {
216 |   Active, // 0
217 |   Inactive, // 1
218 |   Pending // 2
219 | }
220 | // Problem: Can be assigned any number at runtime, e.g., UserStatus.Active = 99
221 | ```
222 | 
223 | ### ✅ GOOD: String Literal Unions or `const enum`
224 | 
225 | ```typescript
226 | // types.d.ts or types.ts
227 | /** @typedef {'active' | 'inactive' | 'pending'} UserStatus */
228 | // Or using native TS:
229 | type UserStatus = 'active' | 'inactive' | 'pending';
230 | 
231 | // If an enum is truly necessary, use a const string enum for compile-time safety and runtime efficiency:
232 | const enum UserRole {
233 |   Admin = "admin",
234 |   User = "user",
235 |   Guest = "guest",
236 | }
237 | ```
238 | 
239 | ```javascript
240 | // user-management.js
241 | /**
242 |  * @typedef {import('./types').UserStatus} UserStatus
243 |  */
244 | 
245 | /**
246 |  * @param {UserStatus} status
247 |  */
248 | export function updateUserStatus(status) {
249 |   console.log(`User status updated to: ${status}`);
250 | }
251 | 
252 | updateUserStatus('active');
253 | // updateUserStatus('invalid'); // Type error
254 | ```
255 |

257 | 
258 | Generics allow you to write flexible and reusable code that works with a variety of types while maintaining type safety.
259 | 
260 | ```javascript
261 | // utils.js
262 | /**
263 |  * @template T
264 |  * @param {T} arg
265 |  * @returns {T}
266 |  */
267 | export function identity(arg) {
268 |   return arg;
269 | }
270 |

274 | // With constraints (requires native TS syntax or complex JSDoc)
275 | // For complex generics with constraints, consider writing them in a .ts file
276 | // and importing their JSDoc type definitions.
277 | ```

280 | 
281 | Maintainable codebases rely on clear structure.
282 |

  5 | # Vitest Best Practices
  6 | 
  7 | Vitest is the definitive testing framework for our Vite-powered projects. It offers a fast, Jest-compatible API with deep integration into the Vite ecosystem. Adhering to these guidelines ensures our tests are robust, performant, and easy to maintain.
  8 | 
  9 | ## 1. Code Organization & Naming
 10 | 
 11 | **Always co-locate test files with their source.** This improves discoverability and ensures tests are updated alongside their implementation.
 12 | 
 13 | *   **File Naming**: Use `*.test.{ts,tsx,js,jsx}`.
 14 | *   **Location**: Place test files directly next to the component or module they test.
 15 | 
 16 | ❌ BAD:
 17 | ```
 18 | // src/components/Button/Button.tsx
 19 | // tests/components/Button.test.tsx
 20 | ```
 21 | 
 22 | ✅ GOOD:
 23 | ```typescript
 24 | // src/components/Button/Button.tsx
 25 | // src/components/Button/Button.test.tsx
 26 | ```
 27 | 
 28 | ## 2. Test Structure & Isolation
 29 | 
 30 | **Organize tests logically using `describe` and `it` (or `test`) blocks.** Ensure each test is isolated and deterministic.
 31 | 
 32 | *   **`describe`**: Group related tests into suites.
 33 | *   **`it` / `test`**: Define individual test cases. Prefer `it` for consistency with Jest.
 34 | *   **Hooks (`beforeEach`, `afterEach`)**: Use these for setup and teardown to ensure test isolation.
 35 | 
 36 | ❌ BAD: (Shared state, no cleanup)
 37 | ```typescript
 38 | let user;
 39 | test('creates user', () => {
 40 |   user = createUser();
 41 |   expect(user).toBeDefined();
 42 | });
 43 | test('updates user', () => { // Depends on previous test
 44 |   user.name = 'New Name';
 45 |   expect(user.name).toBe('New Name');
 46 | });
 47 | ```
 48 | 
 49 | ✅ GOOD: (Isolated tests with hooks)
 50 | ```typescript
 51 | import { describe, it, expect, beforeEach, afterEach } from 'vitest';
 52 | import { createUser, deleteUser } from './user-service';
 53 | 
 54 | describe('User Service', () => {
 55 |   let user;
 56 | 
 57 |   beforeEach(() => {
 58 |     user = createUser(); // Create a fresh user for each test
 59 |   });
 60 | 
 61 |   afterEach(() => {
 62 |     deleteUser(user.id); // Clean up after each test
 63 |   });
 64 | 
 65 |   it('should create a user', () => {
 66 |     expect(user).toBeDefined();
 67 |     expect(user.id).toBeTypeOf('string');
 68 |   });
 69 | 
 70 |   it('should update a user', () => {
 71 |     user.name = 'Jane Doe';
 72 |     expect(user.name).toBe('Jane Doe');
 73 |   });
 74 | });
 75 | ```
 76 | 
 77 | ## 3. Asynchronous Testing with `vi.waitFor`
 78 | 
 79 | **Always use `vi.waitFor` for polling conditions in asynchronous tests.** Avoid arbitrary `setTimeout` calls or manual polling loops. `vi.waitFor` is designed for reliable synchronization.
 80 | 
 81 | ❌ BAD: (Flaky, relies on arbitrary timeout)
 82 | ```typescript
 83 | test('data loads after delay', async () => {
 84 |   let data = null;
 85 |   fetchData().then(res => (data = res));
 86 |   await new Promise(resolve => setTimeout(resolve, 100)); // Arbitrary wait
 87 |   expect(data).toEqual('some data');
 88 | });
 89 | ```
 90 | 
 91 | ✅ GOOD: (Reliable polling with `vi.waitFor`)
 92 | ```typescript
 93 | import { it, expect, vi } from 'vitest';
 94 | import { fetchData } from './api'; // Assume fetchData returns a Promise
 95 | 
 96 | it('should load data after delay', async () => {
 97 |   let data = null;
 98 |   fetchData().then(res => (data = res));
 99 | 
100 |   // Polls until data is not null, with a 2-second timeout
101 |   await vi.waitFor(() => expect(data).not.toBeNull(), { timeout: 2000 });
102 | 
103 |   expect(data).toEqual('some data');
104 | });
105 | ```
106 | 
107 | ## 4. Mocking Strategies
108 | 
109 | **Leverage Vitest's `vi` API for all mocking.** This provides Jest-compatible syntax and seamless integration. Always clean up mocks after each test.
110 | 
111 | *   **`vi.fn()`**: Mock individual functions.
112 | *   **`vi.spyOn()`**: Spy on existing object methods.
113 | *   **`vi.mock()`**: Mock entire modules.
114 | 
115 | ### Function Mocking
116 | 
117 | ❌ BAD: (Manual mock, no easy reset)
118 | ```typescript
119 | const originalFetch = global.fetch;
120 | global.fetch = () => Promise.resolve({ json: () => ({ id: 1 }) });
121 | // ... test ...
122 | global.fetch = originalFetch; // Easy to forget cleanup
123 | ```
124 | 
125 | ✅ GOOD: (Using `vi.fn` with `afterEach` cleanup)
126 | ```typescript
127 | import { it, expect, vi, afterEach } from 'vitest';
128 | import { getUser } from './user-api';
129 | 
130 | // Mock the module containing fetchUser
131 | vi.mock('./user-api', async (importOriginal) => {
132 |   const mod = await importOriginal();
133 |   return {
134 |     ...mod,
135 |     fetchUser: vi.fn(), // Mock specific function within the module
136 |   };
137 | });
138 | 
139 | // Import the mocked function after vi.mock
140 | import { fetchUser } from './user-api';
141 | 
142 | afterEach(() => {
143 |   vi.clearAllMocks(); // Clear mock calls after each test to prevent state leakage
144 | });
145 | 
146 | it('should fetch user data', async () => {
147 |   fetchUser.mockResolvedValueOnce({ id: 1, name: 'Test User' });
148 |   const user = await getUser(1);
149 |   expect(fetchUser).toHaveBeenCalledWith(1);
150 |   expect(user.name).toBe('Test User');
151 | });
152 | ```
153 | 
154 | ### Module Mocking
155 | 
156 | **Mock modules at the top of the file.** This ensures the mock is applied before the module under test imports it.
157 | 
158 | ✅ GOOD: (Module mock before imports)
159 | ```typescript
160 | import { vi, it, expect } from 'vitest';
161 | 
162 | // Mock the entire 'lodash' module to control its behavior
163 | vi.mock('lodash', () => ({
164 |   debounce: vi.fn((fn) => fn), // Mock debounce to execute immediately
165 | }));
166 | 
167 | import { debounce } from 'lodash'; // Import the mocked debounce
168 | import { saveInput } from './input-handler'; // Module using debounce
169 | 
170 | it('should call save function without debounce delay', () => {
171 |   saveInput('test');
172 |   expect(debounce).toHaveBeenCalledOnce();
173 | });
174 | ```
175 | 
176 | ## 5. DOM Environment & Component Testing
177 | 
178 | **Use `happy-dom` for lightweight DOM environments.** It's generally faster and sufficient for most component tests. Switch to `jsdom` only if specific browser APIs are missing in `happy-dom`.
179 | 
180 | *   Configure in `vite.config.ts` or `vitest.config.ts`.

182 | ✅ GOOD: (Configuring `happy-dom`)

184 | // vite.config.ts or vitest.config.ts
185 | import { defineConfig } from 'vitest/config';

197 | **Utilize `.concurrent` for tests that can run in parallel.** This significantly speeds up test suites where tests are independent.
198 | 
199 | *   Use `it.concurrent` for individual tests.
200 | *   Use `describe.concurrent` for entire suites.

202 | 
203 | ❌ BAD: (Sequential tests, slow)
204 | ```typescript
205 | describe('My Feature', () => {
206 |   it('test A', async () => { /* ... */ });
207 |   it('test B', async () => { /* ... */ });

218 |   });

221 |     expect(2).toBe(2);
222 |   });
223 | });

229 | 
230 | *   Add `coverage` configuration to `vite.config.ts` or `vitest.config.ts`.
231 | *   Run with `vitest run --coverage`.

233 | ✅ GOOD: (V8 coverage configuration)

 50 |   user: { id: string; name: string } | null;

 53 |   logout: () => void;
 54 | }

 56 | export interface UISlice {
 57 |   isLoading: boolean;
 58 |   setLoading: (loading: boolean) => void;
 59 | }

 61 | // Combine all slice interfaces into the global AppState
 62 | export type AppState = AuthSlice & UISlice;

 64 | // Type for creating slices that will be composed into AppState
 65 | export type AppStateCreator<T> = StateCreator<AppState, [], [], T>;
 66 | ```
 67 | 
 68 | `src/store/slices/createAuthSlice.ts`:

### Component Pattern
```typescript
import * as React from "react";
import { cva, type VariantProps } from "class-variance-authority";
import { cn } from "@/lib/utils";

const componentVariants = cva("base-classes", {
  variants: { /* ... */ },
  defaultVariants: { /* ... */ }
});

export interface ComponentProps
  extends React.HTMLAttributes<HTMLElement>,
    VariantProps<typeof componentVariants> {}

const Component = React.forwardRef<HTMLElement, ComponentProps>(
  ({ className, variant, ...props }, ref) => {
    return <element className={cn(componentVariants({ variant, className }))} ref={ref} {...props} />;
  }
);
Component.displayName = "Component";

export { Component, componentVariants };
```
